# FeedService — архитектурная документация

## 1. Назначение

**FeedService** — микросервис для централизованной работы с товарными данными.

Сервис получает данные о товарах из разных источников, приводит их к единой канонической модели, нормализует, валидирует, сохраняет и предоставляет результат внутренним потребителям.

Дополнительно FeedService отвечает за формирование документов и экспортов в форматах, необходимых конкретным потребителям.

Основная задача:

> Получить разнородные товарные данные → определить тип товара → применить правила его нормализации → получить канонический товар → сохранить его → предоставить или экспортировать данные потребителям.

Целевой поток:

```text
Внешние источники
       ↓
    Connector
       ↓
     Parser
       ↓
   Source DTO
       ↓
     Mapper
       ↓
   RawProduct
       ↓
  Type Resolver
       ↓
Type-specific Normalizer
       ↓
   Product
       ↓
    Validator
       ↓
   Repository
       ↓
  PostgreSQL
       ↓
 ┌─────┴───────────────────┐
 ↓                         ↓
API / Events          Export / Documents
 ↓                         ↓
Потребители            CRM / Web / Analytics / ...
```

---

# 2. Зачем нужен FeedService

Сейчас разные системы могут хранить информацию о товаре по-разному.

Например:

```text
1С
├── собственные идентификаторы
├── свои категории
├── свои названия
└── свои форматы данных

Web
├── свои данные карточки
├── свои категории
├── свои атрибуты
└── свои идентификаторы
```

Если каждый потребитель будет самостоятельно разбирать эти данные:

```text
1С ─────→ CRM
1С ─────→ Web
1С ─────→ Analytics

Web ────→ CRM
Web ────→ Analytics
```

получается большое количество интеграций и дублирование логики.

FeedService становится промежуточным каноническим слоем:

```text
                 ┌──→ CRM
                 │
1C ──┐           │
     ├──→ FeedService ──→ Web
Web ─┘           │
                 └──→ Analytics
```

Источники отвечают за предоставление исходных данных.

FeedService отвечает за:

* получение данных;
* приведение к канонической модели;
* нормализацию;
* валидацию;
* хранение;
* формирование документов;
* экспорт данных потребителям.

Потребители работают с единой канонической моделью или её экспортным представлением.

---

# 3. Основные источники

На первом этапе рассматриваются два источника.

## 3.1. 1С

Основной источник товарных данных.

Возможные способы передачи:

* API;
* файл.

Возможные форматы:

* JSON;
* XML;
* CSV.

Не требуется реализовывать все форматы сразу.

Архитектура должна позволять добавить нужный формат без изменения доменной модели.

## 3.2. Web

Web может содержать данные, которых нет или недостаточно в 1С.

Поэтому Web рассматривается как отдельный источник данных.

В дальнейшем могут появляться другие источники:

```text
Dallion
CMS
PIM
другие внутренние системы
```

Добавление нового источника не должно требовать изменения доменной модели.

---

# 4. Потребители

Основные потребители FeedService:

```text
FeedService
├── CRM
├── Web
└── Analytics
```

Потребитель не является доменной сущностью FeedService.

Это клиент сервиса, который получает данные через:

* API;
* события;
* сформированные документы;
* периодические экспорты;
* другие механизмы доставки.

Конкретный механизм определяется отдельно для каждого сценария.

---

# 5. Ответственность FeedService

FeedService отвечает за:

1. получение исходных товарных данных;
2. разбор внешних форматов;
3. преобразование данных к унифицированному входному представлению;
4. определение типа товара;
5. нормализацию;
6. валидацию;
7. хранение канонической модели;
8. отслеживание идентификаторов источников;
9. формирование документов и экспортов;
10. предоставление данных потребителям;
11. публикацию изменений;
12. обработку ошибок импорта и нормализации.

FeedService **не должен содержать бизнес-логику конкретного потребителя**.

Например, FeedService может сформировать XML для Mindbox, но не должен решать:

```text
кому отправлять CRM-коммуникацию;
какую акцию применить;
какой сегмент использовать;
какое маркетинговое правило сработало.
```

---

# 6. Основной архитектурный принцип

FeedService разделяет несколько разных задач.

```text
Connector
    ↓
получение данных

Parser
    ↓
разбор формата

Source DTO
    ↓
представление структуры внешней системы

Mapper
    ↓
техническое преобразование

RawProduct
    ↓
унифицированное сырое представление

Type Resolver
    ↓
определение типа товара

Normalizer
    ↓
бизнес-нормализация конкретного типа

Product
    ↓
каноническая доменная модель

Validator
    ↓
проверка корректности

Repository
    ↓
сохранение

Export / API / Events
    ↓
доставка потребителям
```

Каждый компонент отвечает за свою часть процесса.

# 7. Слои приложения

Предварительная структура:

```text
FeedService
│
├── API
├── Application
├── Domain
└── Infrastructure
```

## Domain

Содержит бизнес-модель:

* `Product`;
* специализированные типы товаров;
* `Category`;
* enum;
* доменные правила;
* значения и ограничения, относящиеся к предметной области.

Domain не знает:

* о JSON;
* XML;
* CSV;
* 1С;
* Web;
* PostgreSQL;
* ORM;
* AutoMapper;
* HTTP;
* конкретном брокере сообщений.

---

## Application

Содержит сценарии работы приложения:

* `ImportService`;
* `ProductService`;
* `NormalizationService`;
* `ExportService`;
* интерфейсы;
* application DTO;
* orchestration;
* application-level validation.

Application координирует выполнение сценария, но не зависит от конкретной инфраструктуры.

---

## Infrastructure

Содержит технические реализации:

* connectors;
* parsers;
* source DTO;
* mappers;
* repositories;
* database;
* внешние интеграции;
* message broker;
* outbox;
* конкретные механизмы экспорта.

При этом бизнес-правила нормализации не должны становиться зависимыми от конкретной инфраструктуры.

---

## API

Предоставляет HTTP API FeedService.

API работает через application layer и не обращается напрямую к Repository.

# 8. Доменная модель Product

Основная сущность — `Product`.

Она является базовым классом для специализированных типов товаров.

```text
Product
│
├── FoodProduct
├── ToyProduct
├── ClothingProduct
├── CareProduct
└── ...
```

Наследники создаются только для основных товарных типов.

Количество типов не фиксируется навсегда и может расширяться.

---

# 9. Базовый Product

`Product` содержит только общие свойства, применимые к любому товару.

```csharp
public abstract class Product
{
    public Guid Id { get; set; }

    public string SKU { get; set; }

    public string Name { get; set; }

    public Category Category { get; set; }

    public decimal Price { get; set; }

    public decimal? OldPrice { get; set; }

    public string? PictureUrl { get; set; }

    public string? Url { get; set; }

    public string? Description { get; set; }

    public DateTime CreatedAt { get; set; }

    public DateTime UpdatedAt { get; set; }
}
```

Основные свойства:

* `Id` — канонический идентификатор FeedService;
* `SKU` — бизнесовый/товарный идентификатор;
* `Name`;
* `Category`;
* `Price`;
* `OldPrice`;
* `PictureUrl`;
* `Url`;
* `Description`;
* `CreatedAt`;
* `UpdatedAt`.

`CreatedAt` и `UpdatedAt` относятся к записи товара в FeedService и не должны автоматически трактоваться как даты создания/изменения товара в исходной системе.

При необходимости исходные даты источника хранятся отдельно.

---

# 10. Идентичность товара

Канонический `Product.Id` не должен зависеть от идентификатора конкретного источника.

Источник может иметь собственный идентификатор:

```text
1С → 123456
Web → 987654
Dallion → ABC-123
```

FeedService использует собственный канонический идентификатор:

```text
Product.Id = UUID
```

Связь с внешними системами хранится отдельно.

Условно:

```text
Product
├── Id = canonical UUID
│
└── ExternalIdentifiers
    ├── 1C = 123456
    ├── Web = 987654
    └── Dallion = ABC-123
```

Это позволяет:

* добавлять новые источники;
* не использовать SKU как единственный технический идентификатор;
* переживать изменение SKU;
* сопоставлять один товар из разных источников.

---

# 11. External Identifiers

Для внешних идентификаторов должна существовать отдельная модель.

Условно:

```text
ProductExternalIdentifier
├── ProductId
├── Source
├── ExternalId
└── ...
```

Для комбинации:

```text
Source + ExternalId
```

должна обеспечиваться уникальность.

Механизм определения соответствия товара между источниками является отдельным архитектурным вопросом.

SKU может использоваться как один из признаков идентификации, но не должен автоматически считаться единственным глобальным идентификатором.

---

# 12. Source of Truth / Ownership

Для каждого канонического атрибута необходимо определить источник-владельца.

Например:

| Атрибут   | Источник     | Правило                       |
| --------- | ------------ | ----------------------------- |
| SKU       | 1С           | 1С — основной источник        |
| Цена      | 1С           | 1С — основной источник        |
| Название  | определяется | возможно несколько источников |
| Описание  | Web/CMS      | определяется                  |
| Фото      | Web/CMS      | определяется                  |
| Категория | FeedService  | каноническая модель           |
| PetType   | FeedService  | результат нормализации        |
| AgeGroup  | FeedService  | результат нормализации        |

На первом этапе некоторые поля могут формироваться из нескольких источников.

Архитектура должна позволять это поддерживать.

В перспективе для каждого поля может быть определён единый master/source of truth.

Главный принцип:

> Наличие данных в FeedService не означает, что FeedService является владельцем исходного значения.

FeedService является владельцем **канонического представления**, но источник конкретного значения может находиться в другой системе.

---

# 13. Специализированные Product-модели

Специфичные характеристики не складываются в один универсальный набор полей.

Например:

```text
FoodProduct
├── PetType
├── AgeGroup
├── Flavors
├── Volume
└── Unit
```

А:

```text
ToyProduct
├── PetType
├── Size
├── Color
└── Material
```

Таким образом, вкус не является свойством игрушки, а материал не является обязательным свойством корма.

Это выражается непосредственно структурой доменной модели.

---

# 14. FoodProduct

Модель товаров категории кормов.

```csharp
public class FoodProduct : Product
{
    public PetType PetType { get; set; }

    public AgeGroup? AgeGroup { get; set; }

    public List<string>? Flavors { get; set; }

    public decimal? Volume { get; set; }

    public Unit? Unit { get; set; }
}
```

Возможные характеристики:

* тип животного;
* возрастная группа;
* вкус;
* объём;
* единица измерения.

---

# 15. ToyProduct

Модель товаров категории игрушек.

```csharp
public class ToyProduct : Product
{
    public PetType PetType { get; set; }

    public string? Size { get; set; }

    public string? Color { get; set; }

    public string? Material { get; set; }
}
```

Возможные характеристики:

* тип животного;
* размер;
* цвет;
* материал.

---

# 16. Расширение модели

При появлении нового основного типа товара создаётся новый наследник.

Например:

```text
Product
│
├── FoodProduct
├── ToyProduct
├── ClothingProduct
├── CareProduct
└── ServiceProduct
```

Не следует создавать отдельный класс для каждого узла каталога.

Например, без необходимости не создаём:

```text
DryDogFoodProduct
WetDogFoodProduct
CatToyProduct
DogToyProduct
```

Категория и тип товара — разные понятия.

---

# 17. Category

`Category` является отдельной доменной сущностью.

```csharp
public class Category
{
    public Guid Id { get; set; }

    public string Name { get; set; }

    public Guid? ParentId { get; set; }
}
```

Категория описывает положение товара в каноническом каталоге.

---

# 18. Иерархия категорий

Категории образуют дерево:

```text
Корма
├── Кошки
│   ├── Сухой корм
│   └── Влажный корм
│
└── Собаки
    ├── Сухой корм
    └── Влажный корм
```

Связь реализуется через `ParentId`.

Количество уровней не ограничивается.

Не следует создавать отдельные поля:

```text
Category
SubCategory
SubSubCategory
```

Иерархия должна быть динамической.

---

# 19. Category и Product Type

`Category` и `Product Type` — разные понятия.

Например, одна категория может содержать товары разных специализированных типов в зависимости от структуры каталога и предметной области.

Также тип товара не должен определяться исключительно названием категории.

Условно:

```text
Category
    ↓
может использоваться как один из признаков
    ↓
TypeResolver
    ↓
Product Type
```

Например:

```text
Кошки
├── Корм
│   └── FoodProduct
│
└── Игрушки
    └── ToyProduct
```

При этом категория может быть связана с разными типами товаров в разных ветках каталога.

---

# 20. Product и Category

На первом этапе товар имеет одну каноническую категорию:

```text
Product
   ↓
Category
```

Мультикатегорийность пока не реализуется.

Если впоследствии она понадобится, модель может быть расширена через связь many-to-many:

```text
Product
   ↕
ProductCategory
   ↕
Category
```

---

# 21. Source Category и Canonical Category

Категория источника и каноническая категория FeedService не обязаны быть одинаковыми.

Например:

```text
1С Category
    ↓
Category Mapping
    ↓
FeedService Category
```

На первом этапе предполагается, что категория источника является корректной и может использоваться как основа для определения канонической категории.

Однако архитектура должна позволять добавить отдельный mapping, если структура источника и канонического каталога разойдутся.

Это особенно важно при подключении нескольких источников.

---

# 22. PetType

Тип животного является enum.

Например:

```text
Dog
Cat
Bird
Fish
Reptile
```

Фактический справочник будет определён после анализа каталога.

`PetType` описывает применимость товара к типу животного и не заменяет категорию.

---

# 23. AgeGroup

Возрастная группа также является enum.

Например:

```text
Baby
Young
Adult
Senior
```

Финальный набор значений определяется после анализа реальных данных.

---

# 24. Volume и Unit

Для соответствующих типов товаров используются:

```text
Volume
Unit
```

Например:

```text
Volume = 85
Unit = Gram
```

или:

```text
Volume = 100
Unit = Milliliter
```

Оба поля могут быть `null`.

Не каждый товар имеет измеримый объём.

---

# 25. Flavors

Для товаров, у которых может быть несколько вкусов:

```text
List<string>
```

Например:

```text
Flavors:
[
    "Курица",
    "Индейка"
]
```

Отдельная сущность `Flavor` пока не требуется.

Если впоследствии появится необходимость в централизованном справочнике вкусов, модель может быть расширена.

---

# 26. RawProduct

Перед созданием конкретного доменного типа используется промежуточная модель `RawProduct`.

Она представляет товар в унифицированном, но ещё **ненормализованном** виде.

Условно:

```text
RawProduct
├── Source
├── ExternalId
├── SKU
├── Name
├── SourceCategory
├── Price
├── Description
├── Raw attributes
├── ReceivedAt
├── ImportId
└── RawPayload
```

Главная задача `RawProduct` — отделить структуру входящих данных от бизнес-модели.

На этом этапе:

```text
"Royal Canin Medium Adult 15 кг"
```

ещё может оставаться обычной строкой.

Из неё ещё не извлечены:

```text
AgeGroup = Adult
Volume = 15
Unit = Kilogram
```

---

# 27. Хранение исходных данных

Исходные данные желательно сохранять отдельно от нормализованного товара.

Причины:

* повторная нормализация без повторного запроса к источнику;
* отладка ошибок;
* анализ некорректных данных;
* изменение правил нормализации;
* аудит;
* воспроизводимость импорта.

Условный поток:

```text
Source
   ↓
RawProduct
   ↓
хранение исходного представления
   ↓
Normalizer
   ↓
Product
```

Если правила `FoodNormalizer` изменились:

```text
старый RawProduct
       ↓
новая версия Normalizer
       ↓
новый Product
```

Таким образом, исправление правил не требует повторной выгрузки данных из источника.

---

# 28. Import / Batch

Каждый запуск импорта рассматривается как отдельный batch.

Например:

```text
Import #152
Source: 1C

Received: 100 000
Processed: 99 500
Failed: 500

Created: 1 200
Updated: 8 300
Unchanged: 90 000
```

Import хранит техническую информацию о процессе:

* источник;
* время начала;
* время окончания;
* количество полученных объектов;
* количество успешно обработанных;
* количество ошибок;
* статус;
* идентификатор запуска.

Это позволяет анализировать конкретный запуск импорта независимо от текущего состояния товара.

---

# 29. Пагинация и пакетная обработка

Большие источники не должны обрабатываться как единый огромный объект в памяти.

Импорт должен поддерживать пакетную обработку:

```text
Source
   ↓
Page / Batch 1
   ↓
Processing
   ↓
Page / Batch 2
   ↓
Processing
   ↓
...
```

Размер страницы/батча определяется отдельно.

Пагинация позволяет:

* ограничить потребление памяти;
* контролировать нагрузку на БД;
* повторять обработку отдельных частей;
* масштабировать импорт;
* корректно работать с большими каталогами.

---

# 30. Connector

Connector отвечает за получение данных из конкретного источника.

Примеры:

```text
OneCConnector
WebConnector
```

Connector знает:

* куда обращаться;
* как авторизоваться;
* как получить файл;
* как вызвать API;
* как получить исходные данные;
* как реализовать пагинацию источника, если она поддерживается.

Connector **не занимается бизнес-нормализацией**.

---

# 31. Parser

Parser отвечает только за разбор формата.

Возможные реализации:

```text
JsonParser
XmlParser
CsvParser
```

Поток:

```text
JSON / XML / CSV
        ↓
      Parser
        ↓
   Source DTO
```

Parser не должен знать, что такое `FoodProduct`, `ToyProduct` и т. д.

---

# 32. Source DTO

Каждый источник может иметь собственную структуру.

Например:

```text
OneCProductDto
WebProductDto
```

DTO отражает формат внешней системы.

Например:

```text
OneCProductDto
├── Code
├── Name
├── Price
├── CategoryCode
└── AnimalType
```

Это не доменная модель.

---

# 33. Mapper

Mapper отвечает за техническое преобразование данных между структурами.

Например:

```text
OneCProductDto
       ↓
    Mapper
       ↓
RawProduct
```

Mapper не должен содержать бизнес-логику вида:

```text
если название содержит "корм"...
если строка содержит "15 кг"...
если содержит "курица"...
```

Такие правила находятся в `Normalizer`.

Для реализации Mapper может использоваться AutoMapper.

При этом можно сохранить собственный интерфейс:

```csharp
IProductMapper
```

чтобы остальная система не зависела непосредственно от AutoMapper.

---

# 34. Определение типа товара

После получения `RawProduct` необходимо определить, к какому основному типу относится товар.

Например:

```text
RawProduct
    ↓
Type Resolver
    ↓
FoodProduct
```

или:

```text
RawProduct
    ↓
Type Resolver
    ↓
ToyProduct
```

Механизм определения типа может использовать:

* категорию;
* код категории;
* признаки источника;
* другие бизнес-правила.

Конкретный механизм будет определён после анализа реального каталога.

TypeResolver не должен заниматься извлечением всех специфичных атрибутов товара.

---

# 35. Нормализация товаров по типу

После определения типа товара применяется соответствующий **type-specific Normalizer**.

Примеры:

```text
FoodNormalizer
ToyNormalizer
ClothingNormalizer
CareNormalizer
```

Каждый нормализатор содержит правила обработки своего типа товара.

В том числе:

* regex-парсинг;
* извлечение атрибутов из названия;
* нормализацию значений;
* преобразование единиц;
* заполнение специфичных атрибутов;
* обработку особенностей конкретного типа.

Главный принцип:

```text
RawProduct
    ↓
определение типа
    ↓
Type-specific Normalizer
    ↓
конкретный Product
```

Например:

```text
"Корм сухой для собак Royal Canin Medium Adult 15 кг"
                         ↓
                  FoodNormalizer
                         ↓
FoodProduct
├── PetType = Dog
├── AgeGroup = Adult
├── Volume = 15
└── Unit = Kilogram
```

Для игрушки:

```text
"Игрушка для собак мяч резиновый красный"
                         ↓
                  ToyNormalizer
                         ↓
ToyProduct
├── PetType = Dog
├── Material = Rubber
└── Color = Red
```

---

# 36. Почему отдельные Normalizer

Не следует создавать один огромный нормализатор:

```csharp
NormalizeProduct()
{
    if (...)
    {
        ...
    }
    else if (...)
    {
        ...
    }
    else if (...)
    {
        ...
    }
}
```

При увеличении количества типов он быстро превратится в набор взаимосвязанных `if/else`.

Вместо этого:

```text
FoodNormalizer
    → правила кормов

ToyNormalizer
    → правила игрушек

ClothingNormalizer
    → правила одежды
```

Каждый нормализатор можно развивать независимо.

Добавление нового типа товара не требует переписывать существующие нормализаторы.

Архитектурно это реализуется через Strategy/Registry подход:

```text
IProductNormalizer
├── FoodNormalizer
├── ToyNormalizer
├── ClothingNormalizer
└── ...
```

---

# 37. Normalizer и Mapper — разные ответственности

Это принципиальное разделение.

### Mapper

Отвечает:

> Как переложить данные из одной структуры в другую?

```text
OneCProductDto → RawProduct
```

### Normalizer

Отвечает:

> Как понять и привести товар к канонической бизнес-модели?

```text
RawProduct → FoodProduct
```

Поэтому regex, извлечение характеристик и бизнес-правила находятся в `Normalizer`, а не в Mapper.

---

# 38. Validator

После нормализации получаем конкретный доменный объект:

```text
FoodProduct
ToyProduct
...
```

После этого выполняется validation.

Проверяется:

* наличие обязательных полей;
* корректность типов;
* допустимость значений;
* корректность связки с категорией;
* корректность специфичных атрибутов;
* бизнес-ограничения.

Например:

```text
FoodProduct
    ↓
FoodProductValidator
```

проверяет правила корма.

А:

```text
ToyProduct
    ↓
ToyProductValidator
```

проверяет правила игрушки.

---

# 39. Жизненный цикл товара

Товар не должен автоматически удаляться из канонического хранилища только потому, что он отсутствует в очередном импорте.

Основные состояния могут быть представлены условно:

```text
Active
Inactive
Rejected
Quarantined
```

Например:

```text
источник
   ↓
товар отсутствует
   ↓
FeedService
   ↓
товар не удаляется автоматически
```

Товар может быть исключён из обычных выдач/экспортов по соответствующему признаку.

Физическое удаление товара не является частью обычного импорта.

Для этого предусматривается отдельная ручка/операция удаления.

---

# 40. Не нормализованные товары / Quarantine

Если товар невозможно корректно нормализовать или провалена обязательная валидация, он не должен просто теряться.

Такой товар сохраняется отдельно.

Например:

```text
RawProduct
    ↓
TypeResolver / Normalizer / Validator
    ↓
ERROR
    ↓
Quarantine
```

Для записи необходимо сохранять:

* источник;
* внешний ID;
* исходные данные;
* тип ошибки;
* описание ошибки;
* время;
* ImportId;
* текущий статус обработки.

Дальнейшие действия:

1. анализ причины;
2. поиск нового правила нормализации;
3. исправление правила;
4. повторная обработка;
5. либо постановка задачи на исправление данных в источнике.

Это позволяет отделить техническую проблему FeedService от проблемы качества исходных данных.

---

# 41. Repository

Application работает через интерфейс:

```csharp
IProductRepository
```

Repository отвечает за persistence:

* поиск товара;
* поиск по SKU;
* получение по ID;
* поиск по external ID;
* создание;
* обновление;
* сохранение;
* изменение статуса.

Конкретная реализация находится в Infrastructure:

```text
PostgresProductRepository
```

Repository не должен содержать бизнес-нормализацию.

---

# 42. База данных

Предварительный выбор — PostgreSQL.

Причины:

* структурированная модель;
* строгая типизация;
* связи между сущностями;
* иерархия категорий;
* ограничения целостности;
* индексы;
* удобная работа с каталогом;
* смешанные аналитические и фильтрационные запросы.

---

# 43. Стратегия наследования в PostgreSQL

Для хранения иерархии `Product` выбран подход:

> **TPH — Table Per Hierarchy.**

Все типы товаров хранятся в одной таблице с дискриминатором типа.

Условно:

```text
Product
├── Id
├── Type
├── SKU
├── Name
├── CategoryId
├── Price
├── ...
├── Food-specific fields
├── Toy-specific fields
└── Clothing-specific fields
```

Причины выбора TPH:

* основные сценарии включают смешанные фильтры;
* дашборды работают с товарами разных типов;
* планируется пакетная выгрузка XML в Mindbox;
* один `SELECT` по одной таблице позволяет избежать дополнительных `JOIN`/`UNION`;
* дискриминатор может быть проиндексирован;
* при необходимости могут использоваться partial indexes для часто фильтруемых специфичных атрибутов.

TPT и TPC отклонены как менее подходящие для основных смешанных сценариев.

---

# 44. Цена

Цена хранится как атрибут канонического товара.

```text
Product
├── Price
└── OldPrice
```

FeedService не является отдельным сервисом управления ценами.

Цена является частью товарного представления и поступает из определённого source of truth.

Если в будущем потребуется отдельная модель цен:

* региональные цены;
* история цен;
* временные цены;
* несколько прайс-листов;

это может быть выделено в отдельный доменный/интеграционный контекст.

---

# 45. Обновление существующего товара

При импорте необходимо определить:

```text
существует ли товар?
```

Поток:

```text
External ID / Identity Resolution
          ↓
    поиск товара
          ↓
 ┌───────────────┐
 │               │
нет             да
 │               │
 ▼               ▼
Create          Compare
                  │
             ┌────┴────┐
             │         │
          изменился  unchanged
             │         │
             ▼         ▼
           Update    ничего
```

SKU может участвовать в идентификации, но правила identity resolution должны учитывать external IDs и источник.

---

# 46. Идемпотентность

Повторная обработка одинаковых данных не должна создавать дубликаты.

Например:

```text
Один и тот же файл
       ↓
Импорт №1
       ↓
Импорт №2
```

не должен создавать второй экземпляр товара.

Необходимо определить:

* уникальный канонический идентификатор;
* уникальность external ID в рамках источника;
* роль SKU;
* идентификатор импорта;
* повторную обработку одного batch;
* правила изменения SKU.

---

# 47. Определение изменений

При обновлении желательно определять, действительно ли товар изменился.

```text
пришёл товар
      ↓
найден существующий
      ↓
сравнение
      ↓
 ┌──────────────┐
 │              │
не изменился   изменился
 │              │
 ▼              ▼
ничего        Update
```

Если товар не изменился, не требуется:

* выполнять лишний UPDATE;
* публиковать событие;
* создавать лишний экспорт.

Изменения должны определяться на уровне канонической модели.

---

# 48. Версионирование нормализации

Правила нормализации могут изменяться.

Например:

```text
Normalizer v1
    ↓
AgeGroup = null
```

После изменения правила:

```text
Normalizer v2
    ↓
AgeGroup = Adult
```

Поэтому архитектура должна предусматривать возможность хранения версии применённых правил:

```text
NormalizerVersion
```

На первом этапе полноценное версионирование канонического товара может не требоваться.

Однако возможность определить, **какой версией правил был получен результат**, должна быть предусмотрена.

---

# 49. Доставка изменений потребителям

После сохранения товара FeedService потенциально должен сообщать об изменениях:

```text
FeedService
    │
    ├──→ CRM
    ├──→ Web
    └──→ Analytics
```

Возможные механизмы:

* REST API;
* очередь;
* события;
* периодические выгрузки;
* сформированные документы.

Конкретный механизм определяется отдельно.

---

# 50. Outbox

Для надёжной публикации изменений используется паттерн **Outbox**.

Проблема:

```text
Save Product
     ↓
PostgreSQL
     ↓
сервис упал
     ↓
событие не отправлено
```

В результате данные сохранены, но потребители не узнали об изменении.

Поэтому изменение товара и запись события в Outbox должны выполняться в рамках одной транзакции.

Условно:

```text
Transaction
├── UPDATE Product
└── INSERT OutboxEvent
```

После commit отдельный процесс публикует события:

```text
PostgreSQL
    ↓
Outbox
    ↓
Publisher
    ↓
Message Broker
    ↓
Consumers
```

Конкретный брокер пока не фиксируется.

---

# 51. Consumer Contract

Потребители не должны зависеть от внутренних C#-классов FeedService.

Например:

```text
FoodProduct : Product
```

является внутренней доменной моделью.

Для внешнего взаимодействия используется отдельный контракт:

```json
{
  "id": "...",
  "sku": "...",
  "type": "food",
  "category": "...",
  "attributes": {
    "petType": "dog",
    "ageGroup": "adult",
    "volume": 15,
    "unit": "kg"
  }
}
```

Таким образом:

```text
Domain Model
      ↓
Consumer DTO / Export Model
      ↓
Consumer
```

Это позволяет изменять внутреннюю модель без обязательного изменения всех потребителей.

---

# 52. Формирование документов и экспортов

FeedService отвечает не только за хранение и API, но и за формирование потребительских представлений данных.

Например:

```text
Canonical Product
       ↓
 Export Service
       ├── XML
       ├── JSON
       ├── CSV
       └── другой формат
```

При этом формат документа является техническим контрактом конкретного потребителя.

Например:

```text
Canonical Product
       ↓
Mindbox Exporter
       ↓
Mindbox XML
```

или:

```text
Canonical Product
       ↓
Analytics Exporter
       ↓
Analytics CSV
```

Экспортёр отвечает за **представление канонических данных**, но не должен изменять доменную модель или добавлять бизнес-логику потребителя.

---

# 53. Экспорт и бизнес-логика потребителя

Важно разделять:

### FeedService:

```text
Как представить товар в формате, который понимает потребитель?
```

### Потребитель:

```text
Что делать с этим товаром?
```

Например, FeedService может сформировать:

```xml
<Product>
    ...
</Product>
```

для Mindbox.

Но FeedService не должен определять:

* сегменты клиентов;
* маркетинговые кампании;
* скидки;
* коммуникации;
* правила CRM.

Таким образом, экспорт остаётся частью интеграционного слоя, а бизнес-логика остаётся у потребителя.

---

# 54. Полный импорт

Целевой поток:

```text
                        1C / Web
                            │
                            ▼
                       Connector
                            │
                            ▼
                         Parser
                            │
                            ▼
                       Source DTO
                            │
                            ▼
                          Mapper
                            │
                            ▼
                       RawProduct
                            │
                            ▼
                       TypeResolver
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
       FoodNormalizer  ToyNormalizer  ClothingNormalizer
             │              │              │
             ▼              ▼              ▼
        FoodProduct     ToyProduct     ClothingProduct
             │              │              │
             └──────────────┼──────────────┘
                            ▼
                         Validator
                            │
                    ┌───────┴───────┐
                    │               │

                    │               │

                    │
                    ▼

          │         │         │
          ▼         ▼         ▼

```

# 55. Обработка ошибок

Ошибки разделяются по этапам обработки.

## 55.1. Ошибки получения данных

Возникают на Connector:

```text
API unavailable
timeout
authentication error
network error
```

Действия:

* retry для временных ошибок;
* завершение batch с ошибкой для невосстановимых ошибок;
* журналирование.

---

## 55.2. Ошибки формата

Возникают на Parser:

```text
invalid JSON
invalid XML
invalid CSV
unexpected structure
```

Действия:

* остановка соответствующей части обработки;
* фиксация ошибки;
* сохранение информации о batch;
* повтор после исправления источника/формата.

---

## 55.3. Ошибки преобразования

Возникают на Mapper:

```text
невозможно преобразовать значение;
отсутствует обязательное поле источника;
несовместимый тип;
```

Товар не должен незаметно теряться.

Ошибка должна быть связана с конкретным `ImportId` и внешним идентификатором.

---

## 55.4. Ошибки определения типа

Возникают на TypeResolver:

```text
неизвестный тип;
неоднозначный тип;
нет необходимых признаков.
```

Товар отправляется в quarantine.

---

## 55.5. Ошибки нормализации

Возникают на Normalizer:

```text
невозможно распарсить атрибут;
неизвестное значение;
неизвестный формат названия;
regex не сработал.
```

Товар сохраняется как ненормализованный.

Далее:

* анализируется причина;
* добавляется новое правило;
* либо исправляется источник.

---

## 55.6. Ошибки бизнес-валидации

Возникают на Validator:

```text
отсутствует обязательный атрибут;
недопустимое значение;
несовместимая категория и тип товара;
```

Товар не попадает в каноническую активную модель и отправляется в quarantine/rejected state.

---

## 55.7. Ошибки базы данных

Возникают на Repository:

```text
connection error
constraint violation
timeout
deadlock
```

Временные ошибки могут обрабатываться retry.

Ошибки нарушения бизнес/DB constraints должны фиксироваться отдельно.

---

# 56. Частичный импорт

Для больших товарных фидов используется частичная обработка.

Например:

```text
100 000 товаров

99 500 → успешно
500 → ошибки
```

Корректные товары могут быть сохранены.

Некорректные отправляются в quarantine.

Это предпочтительнее полного rollback для больших импортов, поскольку ошибка одного товара не должна блокировать весь каталог.

Однако ошибки уровня самого batch, например повреждённый файл или невозможность прочитать источник, могут привести к остановке batch целиком.

---

# 57. Удаление товара

Товар не удаляется автоматически только из-за отсутствия в очередной выгрузке.

Обычный импорт работает с:

```text
Create
Update
Skip / Unchanged
```

Физическое или логическое удаление выполняется отдельной операцией/ручкой.

Это позволяет:

* избежать случайного удаления;
* контролировать удаление;
* сохранять историю;
* не ломать ссылки потребителей.

# 58. Наблюдаемость

FeedService должен предоставлять техническую статистику обработки.

Минимально необходимо видеть:

```text
Import
├── received
├── processed
├── created
├── updated
├── unchanged
├── failed
└── quarantined
```

Также необходимо отслеживать:

* длительность импорта;
* ошибки по этапам;
* количество товаров по типам;
* количество товаров, не прошедших нормализацию;
* количество товаров, не прошедших validation;
* ошибки внешних источников;
* ошибки экспорта;
* состояние Outbox.

Это позволит понимать не только «упал сервис», но и **на каком этапе и почему не обработались данные**.

# 61. Основные архитектурные принципы

### 1. Источник не диктует доменную модель

1С и Web могут иметь разные структуры.

FeedService приводит их к единой канонической модели.

### 2. Source of Truth определяется отдельно

Для каждого атрибута должен быть понятен источник-владелец.

### 3. Source ID не равен Canonical ID

FeedService имеет собственный идентификатор товара и хранит external IDs источников.

### 4. Parser не знает бизнес-правил

Parser только разбирает формат.

### 5. Mapper не знает правил нормализации

Mapper преобразует структуры.

### 6. Normalizer знает бизнес-правила своего типа

Именно здесь находятся:

* regex;
* parsing названий;
* извлечение характеристик;
* нормализация значений;
* преобразование единиц.

### 7. Тип товара определяет набор специфичных свойств

```text
FoodProduct ≠ ToyProduct
```

Поэтому нерелевантные атрибуты не появляются в модели.

### 8. Category и Product Type — разные понятия

`Category` отвечает за положение в каталоге.

`Product` и его наследник отвечают за структуру данных товара.

### 9. Source Category и Canonical Category могут различаться

Источник может использовать собственную иерархию.

FeedService способен привести её к канонической.

### 10. Domain не зависит от инфраструктуры

Доменная модель не должна знать о:

* PostgreSQL;
* JSON;
* 1С;
* Web;
* AutoMapper;
* конкретном API;
* брокере.

### 11. Исходные данные должны сохраняться

Raw data необходимы для:

* повторной нормализации;
* диагностики;
* аудита;
* воспроизводимости.

### 12. Ошибочный товар не должен исчезать

Ненормализованные товары попадают в quarantine и должны иметь причину ошибки.

### 13. Импорт должен быть идемпотентным

Повторная обработка одних данных не должна создавать дубликаты.

### 14. Изменение товара должно быть обнаруживаемым

Неизменившиеся товары не должны порождать лишние UPDATE и события.

### 15. Изменение и событие должны быть согласованы

Для публикации изменений используется Outbox.

### 16. FeedService не владеет бизнес-логикой потребителя

Он формирует данные и документы.

Потребитель определяет, что делать с этими данными.

### 17. Архитектура должна расширяться без переписывания существующей логики

Новый тип товара → новый `Product` + `Normalizer`.

Новый источник → новый `Connector` + `Parser` + DTO + Mapper.

Новый формат → новый Parser.

Новый потребитель → новый Consumer Contract / Exporter.

**Ключевая идея FeedService:**

> FeedService превращает разрозненные и неоднородные данные из разных источников в единую каноническую типизированную товарную модель, сохраняет исходные данные для повторной обработки, контролирует качество нормализации и предоставляет потребителям данные через API, события и специализированные экспорты.

FeedService при этом не становится владельцем бизнес-логики CRM, Web или Analytics. Он является **каноническим слоем товарных данных и интеграционным слоем их доставки**.
